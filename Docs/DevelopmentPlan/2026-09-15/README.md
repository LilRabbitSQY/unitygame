## 4. 完整游戏的交付范围

### 4.1 必须完成的主循环

新游戏/选档继续 → 世界观与操作引导 → 预约早中晚三次地点+NPC → 逐次NPC先发言、玩家回复 → 每次好感/彩蛋结算 → 抽对手与比较GPA → 确认阵容及补给 → 战斗 → GPA/连胜/NPC成绩/奖励结算 → 商店 → 下一天 → 第28天按排名与好感判定结局。

手机中的个人信息、NPC/棋子图鉴、仓库与新闻，以及菜单设置、退出、保存继续，都要从真实页面访问。已经解锁的结局应可查看。每个确认操作有明确反馈，不能有展示按钮但无业务行为。

### 5.2 最小公共契约 v1（先定数据，再接页面）

以下是待实现的接口职责，不是宣称已有同名API。Part 1创建`Scripts/Contracts/`中的纯数据类型/接口；保持无Unity对象、无服务凭据、无UI引用。尽量保持当前程序集，不为分工强行拆成多层框架。

| 契约 | 至少需要的字段/行为 | 生产者 → 消费者 |
|---|---|---|
| `CampaignSnapshot` | saveId/runId、rulesVersion/contentVersion、day、phase、三时段预约与进度、GPA整数百分位、连胜、NPC成绩/好感及达成序号、库存、已结算操作ID | Part 1 → Part 2/3，只读 |
| `DialogueTurnRequest/Result` | conversationId/turnId、NPC/location、输入与历史、提示、流式片段、完成文本、合法情感/话题标签、完成/失败/取消状态 | Part 1 → Part 3；数值由Part 1规则结算 |
| `DraftRequest/Snapshot` | battleId、day、候选NPC状态、历史/周期、seed、规则版本、已抽对手、先后手、双方已选/可选棋子、锁定状态 | Part 1供输入，Part 2计算，Part 1验证保存，Part 3展示 |
| `BattleStartContext` | battleId/attemptId、levelId与配置版本、双方阵容、随机种子、携带物品效果快照、初始战斗参数 | Part 1确认消费后 → Part 2；Part 3仅驱动显示 |

ID约束：沿用现有棋子/技能/道具key，NPC统一稳定ID并映射旧NPC枚举；显示名称不作存档主键。GPA以百分位整数存储（70=7000，0.99=99）；不使用float累计购买误差。排名、好感同分和恢复必须确定性，不能靠UI排序或每次读档重抽。

契约首批提交同时给出最小调用样例、错误码和示例数据。测试替身放测试程序集或开发专用入口，不进入正式新游戏路径；Part 3可用它联调布局，但最终必须替换为Part 1/2真实服务。扩充`BattleItemDefs`时保持已有12种ID/API兼容，新增7种礼物明确标为非战斗用途；Part 2按用途筛选，不继续假定整个目录永远只有12项。

流程持久化只有Part 1负责；局内模拟只有Part 2负责；Unity每帧只有Part 3提供的一个宿主驱动模拟。`PrepareBattle`只消费一次，`CommitBattleOutcome`按battleId/attemptId去重；收到重复事件不得重复推进日期、奖励或好感。
