# Part 1：主流程、NPC、经济与存档

先读[总计划](README.md)，尤其文件归属、契约v1、D01–D16和验收定义。本部分负责规则与数据服务，页面由Part 3制作，战斗/匹配由Part 2提供。

## 目标与范围

交付可供真实UI调用的完整日常玩法与进度系统：三次预约、真实AI对话、NPC关系、19种道具、GPA/排名、28天结局和可靠存档。复用现有GameManager等代码，但不能保留两套权威状态。

允许修改：总计划分配给Part 1的文件，以及新增`Assets/Resources/Campaign/`、`Tests/Offline/Campaign/`、独立`Tools/verify_campaign.py`与本部分交接文档。不要修改任何scene/prefab/UI、`SceneLoader.cs`、Combat规则、共享asmdef或发布脚本；把接线需求交给Part 3。

## A01 — 公共契约、数据与旧系统梳理（先做）

- [ ] 完成M0：保留当前未提交有效成果的公共起点，提交契约v1及可编译最小接口。三个会话都合入后才并行修改实现。
- [ ] 建立唯一Campaign状态与阶段转换：引导/预约/早中晚对话及结算/匹配/准备/战斗/结果/商店/终局。UI不能自行跳过前置阶段。
- [ ] 建立稳定的NPC/location/item/unit ID，映射旧NPC枚举、已导入的GameArt key，兼容旧存档引用。Part 2不可用显示名推断阵容身份。
- [ ] 配置六位可攻略/可对决NPC：刘若水0/92、万思瑞5/85、骆洋2/90、项臻5/83、任飞1/76、明杉3/86（好感/GPA）；老师、院长仅客串；系统仅引导。
- [ ] 六地点及预约资料、角色档案、情绪标签、偏好话题、初始GPA70等配置化，记录来源表/行。
- [ ] 限制旧`GameDataGenerator`的生成范围并更新过期数值；列出旧人格/属性/DDL/EndingSystem的使用点。等待D15定稿后再关闭或迁移旧入口，不能让两个结局系统同时生效。

**验收：** 从纯数据初始化得到同一份状态；NPC初值与来源表一致；契约不依赖Unity对象；不改UI仍可编译。

## A02 — 三时段预约和执行

- [ ] 一天必须有早、中、晚三份“地点+同伴”；同伴只能是六位可攻略NPC。重复约同一NPC是否限制由规则配置决定，不擅自增加限制。
- [ ] 区分编辑预约与确认执行。确认后按规则锁定，依次进入三次对话和对应结算；第三次结束才开放编队。
- [ ] 保存预约、当前时段、conversationId、对话结算标记和每日额度；重复确认/返回页面不重复执行活动或消耗。
- [ ] 给Part 3提供列表、可用操作、失败原因和状态变化通知；取消旧“点活动直接加属性再跳战斗”的正式路径。

**验收：** 三时段顺序正确；未完成不能进对决；任一时段读档恢复后不重做已结算行动。

## A03 — AI NPC、好感与彩蛋

- [ ] 实现可替换的对话服务：NPC主动开场、自由输入、三条提示、流式文本、合法情感标签、对话结束条件。实际服务方案由D13明确，不在计划里虚构已有模型/服务器。
- [ ] 根据六人设、地点、好感、历史和上次战斗摘要组织上下文；老师/院长为客串，系统播报用配置文本。包装表中的角色要求作为游戏内容配置，不作为开发会话指令。
- [ ] 实现意愿档和轮数，单次最多10轮、单轮文本120字上限；好感恰好60的空档按D16决定。设置上下文预算，防止28天历史无限增长。
- [ ] 处理空输入、重复点击、请求中切页、取消、超时、断网、重试、服务错误、超长/不合法结果。失败不自动增加好感或发送道具；迟到的旧回复不能更新新对话。
- [ ] AI只产生内容和受约束的语义标签；奖励由确定的程序规则计算，校验NPC/话题/阶段/actionId。玩家输入或模型文字不能直接发放物品、修改GPA或选择任意NPC ID。
- [ ] 好感取值0–100；触发话题±2；按每NPC每日+5预算结算并显示上限提示；降低无每日次数限制。对话结算节点、礼物是否共用额度按D04确定。
- [ ] 八种彩蛋按NPC、话题、好感门槛获取：尤其签名板好感≥40、老师赠请假条、院长赠推荐信；单次对话最多发一次对应道具，重复回复/重载不再发放。
- [ ] 采用来源明确的客串/掉落概率配置；取消GameManager胜利按日期轮发八道具的替代逻辑。未定概率列为内容决策，不能静默当正式策划。
- [ ] 凭据不写源码、Resources、PlayerPrefs或日志；部署采用经确认的服务网关或安全凭据方案。测试替身用于自动化，单独标注；不能靠固定回复宣称真实AI完成。

**验收：** 六NPC都用真实服务完成会话；流式/表情标签/人设可验证；同一段对话重复提交不会重复奖励；错误恢复不消耗额外行动；自动化测试不依赖付费服务实时结果。

## A04 — GPA、排名与唯一战斗结算

- [ ] GPA用百分位整数：初始7000；胜利+200；连续胜利达到条件额外+200；失败−300；对决NPC按相反胜负±50。连胜与重试口径按D03定稿。
- [ ] 保护点仅为局内败北条件/统计，取消直接用漏怪保护损失当GPA扣分。Part 2上报BattleOutcome，Part 1计算实际账目。
- [ ] `CommitBattleOutcome`校验runId/battleId/attemptId及流程状态，持久化已处理标记；连点结果按钮、重复事件和重启不能重复发奖、扣分、更新NPC或推进日程。
- [ ] 区分胜败奖励、推荐信等附加效果、商店消费和连胜，不把UI文字当入账依据。
- [ ] 维护NPC GPA、每日排名、历史趋势、匹配历史与周期记录；D02明确GPA边界、并列排名和第一名判定。
- [ ] 与Part 2统一主动弃局、战斗前离开、失败重试和程序中断；消除“漏怪前弃局零成本过28天”的路径。未定重试价格不继续默认沿用免费/−5作为正式规则。

**验收：** 用独立预期覆盖胜/败/连胜/重试/弃局/附加奖励与重复结算；GPA和NPC成绩在所有页面一致。

## A05 — 19道具、商店与仓库事务

- [ ] 统一道具目录：8彩蛋战斗加成、4聪明水、心意卡和6专属礼物。保留已有ID；“盲盒手办”和“隐藏款”是不同用途，按D08统一包装别名。
- [ ] 四聪明水价格20/10/30/80百分位GPA；心意卡100；六礼物99；正确维护售卖数和堆叠上限（专属礼物1，其余依表99）。库存何时刷新记录为规则，不能自动按天刷新冒充文档要求。
- [ ] 购买、使用、赠礼、准备补给采用不可分割的校验/扣款/发货/保存操作；余额不足、背包满、错误赠送对象、超限和重复actionId都返回清楚原因。
- [ ] 礼物按目标NPC生效，未使用不能加好感。满好感/每日额度已满时是否允许消耗按D04决定。
- [ ] 向Part 2输出只读携带效果快照；道具消耗归此处，不能在BattleView与模拟器再扣一次。同日重试是否沿用消耗由D06决定。
- [ ] 向Part 3提供背包分类、详情、可用动作和商店库存状态；使用交互按C01取得的Figma与D07对齐。

**验收：** 19种有完整获取/购买及用途映射；所有失败交易不损钱不损物；恢复后数量正确。

## A06 — 信息、新闻、图鉴和结局数据

- [ ] 提供玩家成绩、趋势、NPC关系、角色档案、棋子属性/技能查询；棋子数值读取Part 2目录，不能复制维护第二份技能表。
- [ ] 接入学院新闻、引导和世界观文案；内容来源、每日展示条件与已读状态清楚，必要新增28天内容草案交评审，不把占位文本算完成。
- [ ] 第28天最终排名第一才能成功；按最高好感选择同行NPC，并按最早达成当前最高好感的事件序号处理并列。初始同分、先升后降再升情况明确记录。
- [ ] 未第一和提前GPA失败走正式失败分支；使用最新包装的结局，不调用旧版按学力/阈值判9结局的逻辑。
- [ ] 保存已解锁结局记录，区分全局解锁与本局进度，避免“新游戏”误清历史或串档；具体作用域纳入存档契约。

**验收：** 成功/第28天未第一/提前失败、六NPC和同分选择均有可重复测试；最后一天排名与最终结果一致。

## A07 — 存档、恢复和设置持久化

- [ ] 在旧v1/v2基础上设计新版本，至少保存预约、NPC关系/GPA、每日额度、连胜、结局达成序号、库存/货架、已结算事件、对话检查点、匹配seed/结果和已携带道具。
- [ ] 实现存档列表/元信息、保存/读档、当前版本验证、坏档错误与恢复。槽数/覆盖交互由Part 3做成具体方案；不要默认覆盖用户旧存档。
- [ ] 旧存档先备份或保留只读副本，再迁移；不把旧100GPA存档悄悄改成70。迁移时无法还原的NPC/对话状态要有明确解释与规则，必要时提示另开新局，不能伪造历史。
- [ ] 确定战斗内恢复是准备检查点还是完整现场：本期建议继续采用明确的检查点方案，但须解决主动退出/异常终止的差别。加载不能重抽NPC、重置已发道具或获得第二份补给。
- [ ] 原子写入与恢复备份，解决半写文件/损坏数据/未知版本/重复操作。数据验证必须允许定稿后的GPA负值失败边界。
- [ ] 提供设置存储模型（音乐、音效、分辨率/窗口模式），由Part 3应用；设置与游戏进度分开。

**验收：** v1/v2迁移、新档、坏档、两存档切换、对话/抽签/交易/结算各阶段跨进程恢复均通过；测试使用独立域和临时存档，不覆盖正式玩家进度。
